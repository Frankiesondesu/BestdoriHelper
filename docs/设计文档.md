# BestdoriHelper 设计文档

> 卡面截图批量识别 + Bestdori 卡册同步工具
> 版本 0.1.0 · 2026-09-17（第 5 轮：方形缩略图建库；第 6 轮：4×4 分块颜色；第 7 轮：SIFT 几何校验，top-1 67.9% → 100%；第 8 轮：结果页核对面板 + 原图框选）

---

## 1. 需求拆解

原始需求可以拆成四个可独立验证的能力：

| # | 需求 | 关键难点 |
| --- | --- | --- |
| R1 | 从游戏截图批量导入卡面缩略图 | 一张截图里有多个卡面，需要切分 |
| R2 | 自动识别角色 / 卡名 / 星级 / 属性 | 游戏缩略图带 UI 叠加、有缩放与压缩损失 |
| R3 | 生成卡面清单 | 去重、人工复核、多格式导出 |
| R4 | 把清单导入 Bestdori | Bestdori 没有公开写入 API，且是登录态数据 |

R2 和 R4 是真正的风险点，设计上重点解决这两个。

后续追加的要求是**要有图形界面可以操作**。这一条不改变上面的技术方案，
只影响交付形态：业务逻辑全部下沉到可复用的函数，再包一层桌面界面
（见 §3.1）。命令行、Web、桌面三条入口共用同一套业务代码。

---

## 2. 关键技术决策

### 2.1 为什么用视觉指纹而不是 OCR？

第一直觉是 OCR 认卡名再查表。实测下来这条路很脆：

- 游戏字体 + 缩放 + JPEG 压缩，OCR 对小字号卡名的识别率会掉到不可用的水平
- 卡名本身可能重名或近似（同一角色的系列卡）
- 卡名有 5 种语言，OCR 模型要分别处理

而 Bestdori 自己就托管了全部卡面。**把识别问题转成"以图搜图"**，准确率和鲁棒性都高一个量级：

```
离线：Bestdori 方形缩略图（180x180）──► 特征提取 ──► 指纹库（一个 npz 文件）
在线：截图切分出的卡面 ──► 特征提取 ──► 与指纹库比对 ──► 卡牌 ID
```

用哪一套卡图很关键 —— 必须用**取景与游戏内卡面格一致的那一套**，见 §2.7。

OCR 降级为**可选的辅助信号**，只在指纹分不出高下时参与判定。

### 2.2 特征选择

每张卡面提取三组特征：

| 特征 | 维度 | 作用 |
| --- | --- | --- |
| pHash（DCT 感知哈希） | 64 bit | 对亮度、缩放、轻微压缩鲁棒 |
| dHash（差分哈希） | 64 bit | 对结构/纹理敏感，与 pHash 互补 |
| **4×4 分块** HSV 直方图 | 16×3×16 = 768 维 | 补上哈希丢失的颜色信息，**且保留"颜色在哪"** |

**为什么颜色要分块**（第 6 轮的改动）：全局直方图丢掉了空间信息 ——
同角色同属性的不同卡配色往往很接近，全局直方图几乎分不开，"左上是蓝、右下是粉"
这种布局信息全被平均掉了。改成 4×4 网格后每块单独 L1 归一化（小块不会被面积
压掉权重），拼接再整体 L2 归一化。

实测（真实截图 140 格）：

| 配置 | top1−top2 差距 中位 | 差距 ≥0.02 占比 | 可直接采信 |
| --- | --- | --- | --- |
| 全局直方图 | 0.014 | 40.0% | 53/140 = 37.9% |
| **4×4 分块** | **0.028** | **55.0%** | **63/140 = 45.0%** |

顺带试过加一路「垂直 dHash」（现有 dHash 只比水平相邻像素，对垂直结构全盲）：
在全局直方图下有点用（37.9% → 44.3%），但换成分块颜色后几乎没有增量
（45.0% → 45.0%），**不值得多占 64 bit 和一份实现复杂度，没采纳**。

pHash 和 dHash 用 numpy 自己实现（DCT-II 变换矩阵），**不引入 scipy / imagehash**，依赖更轻、装得更快。

相似度计算：

```
hash_sim  = 1 - hamming(pHash) + hamming(dHash)  / 128
color_sim = cosine(hist_q, hist_db)
score     = 0.65 * hash_sim + 0.35 * color_sim
```

### 2.2b 粗筛 + 精筛：为什么全局特征不够用（第 7 轮）

**这是整个项目最重要的一次修正。** 第 5、6 轮都在优化全局特征（换方形缩略图、
把颜色直方图改成分块），把"可直接采信"从 10.7% 提到 45%。但真实 top-1 准确率
一直没被正确测量 —— 第 7 轮建了 ground truth 才发现它只有 **67.9%**。

**为什么全局特征有天花板**：pHash（64 bit）、dHash（64 bit）、4×4 分块颜色
直方图（768 维）都是**全图统计量**。它们回答的是"整体上像不像"，而问题
"这是同一张画吗"需要的是**具体纹理的几何对应关系**。同角色、同属性的不同卡，
配色和构图往往都很接近，统计量就分不开了 —— 错配的卡也能拿到 0.85 的分数。

**解法是文献里的标准套路**（游戏王 10k 卡识别、MTG 卡牌扫描器、Project Sekai
机器人识图等项目用的都是这一套）：粗筛取 top-K，再用局部特征做几何校验
二次排序。

```
截图 ──► 粗筛（pHash + dHash + 4×4 分块颜色）──► top-30
                                                    │ 没确认就扩到 top-200
                                                    ▼
                            精筛：SIFT 关键点匹配 + Lowe 比值检验 + RANSAC 仿射校验
                                                    ▼
                                          按「几何内点数」重排，取 top-1
```

| 方案 | top-1 准确率 | 内点 >= 60 的格子 |
| --- | --- | --- |
| 只看全局特征 | 67.9% | — |
| 粗筛 top-30 + 几何校验 | **95.6%** | 131/140 |
| 粗筛 top-100 + 几何校验 | **100%** | 137/140 |

**判据为什么可信**：内点数分布是**强双峰**的 —— 140 个真实格子里 137 格能拿到
内点 ≥ 60 的候选，剩下 3 格都 < 20，**20~60 中间一格都没有**。并且逐对人肉
核验过 13 组匹配可视化：内点 71~233 的匹配线全部密集、平行、铺满脸部；
内点 4~7 的稀疏散乱。详见 `.bdh-test/sift_validate.png` / `sift_mid.png`。

**这件事还纠正了人工标注本身**。第一遍肉眼标注（`.bdh-test/gt_pass1_*.png`）
把"同角色 + 配色接近"误判成了"同一张画"，估计出 85.4% 的准确率；用几何内点
做客观判据重建 ground truth 后，旧流水线的真实成绩是 67.9% —— 肉眼高估了
将近 18 个百分点。

### 2.2c 识别结果必须可核对（第 8 轮）

准确率到 100% 也不等于可以不看。指纹库不可能收录所有卡（实测 140 格里 3 格
找不到候选），用户的截图也可能来自剪裁、缩放、翻拍等任意来源。所以**核对入口
是功能的一部分**，不是装饰：

| 需求 | 实现 |
| --- | --- |
| 看到"识别到的图" | 从原截图里按识别框裁出该格，独立显示 |
| 看到"识别结果的图" | 显示 Bestdori 的**同一张**卡图（建库比对用的那一张，180×180 方形缩略图） |
| 能去 Bestdori 核对 | 给出卡面详情页 `https://bestdori.com/info/cards/{id}`，可点击打开、可复制 |
| 知道识别框在哪 | 整张原图上按状态上色画框（绿=已匹配 / 橙=待确认 / 灰=未识别） |
| 点某张卡面看详情 | 点原图上的框 -> 联动选中结果表对应行 -> 右侧显示卡牌/角色/属性/星级/候选/网址 |

**卡面详情页 URL 是实测确认的**，不是猜的：`https://bestdori.com/info/cards/158`
服务端渲染出来的标题是 "Hagumi Kitazawa - Source Of Happiness"，与本地卡片 158
（`res013006`＝「精神的源泉」）对得上。中文语言**只能跟随站点自身设置** ——
试过 `/cn/...`、`?lang=cn`、`/zh-cn/...` 都换不掉，所以只给基础地址。

**网址要用只读输入框显示，不能用 QLabel**：QLabel 不会在斜杠处折行，面板宽度
只有 300 多像素，`https://bestdori.com/info/cards/307` 会被截断成
`https://bestdori.com/info/…` —— 那就没法核对了。只读 `QLineEdit` 可以横向
滚动、可以全选复制，保证一个字符都不少。

**右侧面板必须套滚动容器**：面板里有核对图（140×140 ×2）、网址、候选列表和
七个按钮，内容最小高度会超过可用高度。实测这种情况下嵌套的 `QHBoxLayout`
会把核对图**撑出自己的区间**，压住下面的网址文字（量到 **11px 重叠**）。
套一层 `QScrollArea` 后，空间不够就改为滚动，布局不再被挤压。
`tests/test_gui_smoke.py::test_detail_panel_does_not_overlap_on_small_windows`
用几何断言把这个坑锁住了。

### 2.2d 卡框贴合 —— 别把相邻卡面切进来（第 9 轮）

**问题**：等分网格切出来的是「格子」，不是「卡框」。

实测（2400×1080 真实截图，4×7 网格）：

| | 尺寸 |
| --- | --- |
| 等分格子 | 170×170 |
| 实际卡框 | 约 150×145 |
| 卡框之间的间隙 | 约 20~25px |

格子每边有约 10px 背景留白；更要命的是**相邻卡面之间只有 20~25px 间隙**，
格子的上下边常常正好压在邻居卡面的边缘上 —— 切出来的图里混着别的卡的一条边。
放大看很直观（`.bdh-test/refine_zoom.png`，红=等分格子，绿=贴合后）。

**做法**：从格子四条边各自向内扫描 ——

1. 跳过开头那段内容（那可能是相邻卡面探进来的边）
2. 跳过背景带
3. 遇到的第一段连续内容就定为本格卡框的那条边

**背景判定**：低饱和（`max-min ≤ 40`）**且**亮度在两端（`≥ 200` 或 `≤ 40`）。
写成"低饱和且两端亮度"而不是只看亮度 —— 四属性标准色里有纯色卡框（V=255），
只看亮度会把它们当背景切掉；两端都认则是为了同时兼容奶白底的游戏截图和深色底的
合成基准。

三条关键设计，都是踩过才定下来的：

**一、从边界扫描，而不是"找包含中心的整段内容"。**
最初的实现是"在格子（向外扩一点）内找包含中心的那段内容"。它在真实截图上工作
正常，但在合成基准上炸了 —— 卡面中间出现大片低饱和区域（浅色衣料、天空、白底）时，
那段内容被从中间切断，框被砍到 170 → 80px（宽比 0.47）。从边界出发的扫描够不到
卡面中间，天然免疫这个问题。

**二、只向内收缩，绝不向外扩展。**
向外扩展能修正"格子边界已经切进本格卡面内部"的情况（实测第 3~5 张截图有），
但它有吃到相邻卡面的风险 —— 那正是要消除的问题。取舍是：少几个像素不致命，
混进别的卡才致命。作为兜底还加了一条「任一条边要收掉超过 25% 就放弃那条边」，
挡掉在卡面内部平坦区上的误判。

**三、四条边各自独立。**
第 3~5 张截图的格子上边界正好切在本格卡面内部（内容从第 0 行就开始了），此时
"上边找不到分界"本身是对的。最初要求四边同时成功才应用，结果整格都不收缩；
改成逐边独立后，左右和下方照样贴合，只有上边保持原样。

**实测（140 个真实卡面格）**：

| | 结果 |
| --- | --- |
| 能定出边界的格子 | 140/140 |
| 宽度收缩后 | 85.5%（最小 83.5%） |
| 高度收缩后 | 87.0%（最小 77.6%） |
| 放大过的框 | 0 |

识别结果不变（认出的画 137/137 = 100%），自动采信从 139/140 提升到 **140/140**。

**为什么"格内贴合"不影响识别**：SIFT 几何校验对整体裁切/平移是天然免疫的
（RANSAC 求的就是仿射变换），所以贴合带来的取景变化不会动摇"是不是同一张画"的
判定。合成基准（§5.1）重跑后 Top-1 与贴合前持平，误判从 1 降到 0。

**顺带修掉的一个不稳定因素**：Bestdori 上有 **111 个 `resourceSetName` 被多张卡
共用**（例如「第N回ガルパ杯」纪念卡复用活动卡原图），这些卡在图库里特征完全相同，
分数必然并列。原来并列时靠 `np.argsort` 的顺序定胜负 —— 那是实现细节，查询图稍有
变化就会换一张卡（表现为"上次认出来是这张、这次变成那张"）。现在并列时统一按
**卡号升序**收尾：`index.search` 改用 `np.lexsort`，`Verifier.rerank` 和
`recognize_crop` 的排序键都补上 `card_id`。实测这让同一份输入的结果完全可复现。

> 代价要说清楚：这类"同一张画对应多张卡"的歧义**无法从图像上区分**。加了确定性的
> tie-break 后，真实截图上的卡号准确率是 99.3%（136/137），而"认出的画正确"是 100%。
> 那 1 格在 Bestdori 上本来就是两张共用一张图的卡，需要人工确认。

### 2.2e 按卡面实际位置切 —— 先找卡面区，再按间隙切（第 10 轮）

**问题**：§2.2d 的贴合只能修"格子基本对、边上有点歪"的情况。但 GUI 调用识别时
**没有传 `region`**，`grid` 模式把整张 2400×1080 按 4×7 等分 —— 得到 343×270 的框，
连左侧菜单都算进去了；而整图等分框里全是 UI 内容，一个背景分界都找不到，
贴合一格也救不回来。用户看到的就是"还是按空格子切"。

**为什么不能只在整图上做投影**：左侧菜单、顶栏、底部按钮在**每一行**都有内容
像素，整图行投影永远是一条实心带（实测 0~1080 一条），间隙根本显不出来。

**可行判据**：卡面的**横向间隙是一条横贯整片卡面区的长背景带** ——
实测 4 条卡面行间隙都在 x=684~1935 上连续是背景（长 1251px），位置一致、
反复出现、y 间距等距；UI 元素不会这样重复。

于是分两步：

1. **`detect_card_area`（自动定位卡面区）**：对每行求最长连续背景段
   （向量化，O(w·h)），取**最长**的那条做种子聚类。
   *为什么按长度而不是按出现次数*：左侧菜单项之间的空隙行数更多，
   按中位数聚类会挑中菜单区（实测就栽在这）。纵向**不外扩** —— 实测第一条
   长带 y=276、最后一条 y=961，已经刚好包住卡面区；按行高外扩会把顶栏和
   底部按钮放进来，污染区域内的行投影，切出一堆竖长条。
2. **`split_by_gaps`（区内按间隙切）**：行投影找"卡面行"（要求高度一致，
   `_largest_consistent_group`），再在每行内按列投影找"卡面列"，交叉即卡框。

两个关键的"别太脆"设计：

- **行方向的内容占比阈值取 0.25**，不是 0.05。0.05 是在整幅图上量的；区域内
  卡面柔边会溢出到间隙里，把占比抬到 0.12~0.23（实测）。阈值太严的后果很具体：
  第 3 张截图有两行卡面被粘成一条 328px 的带，只切出 14 格。实测内容行占比
  中位 0.61，间隙行 0.02~0.23，0.25 落在中间、两边都有余量。
- **列的划分取众数行的结果，行全部保留**。个别行的卡面上有一条低内容占比的
  竖带（浅色衣料），会被当成间隙多切一刀 —— 实测第 1、5 张各有一行切成 8 列。
  原来要求"所有行列数完全一致"，结果整张图退回旧路径。卡的列位置在所有行上
  是一样的，拿多数行的划分当准绳即可；分歧太大（众数行数 < 一半）才放弃。

**放弃条件**（不猜，退回旧路径）：定位不到区域 / 区域内内容占比太低 /
横向间隙不足三条 / 各行列数分歧太大 / 调用方给的行列数与切出数量不符。
所以最坏情况就是回到从前，不会更差。

**实测**：5 张真实截图 **5/5 切出 28 格**（auto 模式、不传 region、不传行列数），
尺寸 143×141 左右，与真实卡框一致；端到端 top-1 99.3%、matched 140/140，
与贴合前完全持平。合成基准 91.1% 持平、误判 0（合成图卡框铺满格子无间隙，
间隙法主动放弃、退回等分 —— 正确行为）。

### 2.3 多档中心裁切 —— 解决"取景不一致"

> ⚠️ 这一节的出发点已被后续实测修正：真正的问题不是"多了边框"，而是**画幅本身不同**。
> 根治办法是改用方形缩略图建库，见 **§2.7**。多档裁切作为吸收残余抖动的机制仍然保留。

游戏缩略图和 Bestdori 原图**画幅并不一致**：游戏里有边框、星级、属性图标，某些界面还会裁掉两侧。直接整图比哈希，分数会明显下降。

解决方法是抽 4 档中心裁切，查询时与指纹库做**全组合**（4×4）比对取最优：

```
crop 0: 全幅        (0.000 ~ 1.000)
crop 1: 中心 90%    (0.050 ~ 0.950)
crop 2: 中心 75%    (0.125 ~ 0.875)
crop 3: 中心 60%    (0.200 ~ 0.800)
```

代价是指纹库从 n 行变成 n 行 × 4 列哈希——用 numpy 向量化做 XOR + popcount，全库（约 4000 个变体）检索仍在毫秒级。

### 2.4 三路信号融合

单一指纹信号在"同角色多张相似卡"上会翻车。设计上引入两个辅助信号：

```
                    ┌─────────────────────────┐
   卡面裁剪 ────────►│ 1. 指纹匹配（主）        │──┐
                    │    哈希 0.65 + 颜色 0.35 │  │
                    └─────────────────────────┘  │
                    ┌─────────────────────────┐  ├──► 融合打分 ──► 判定
   卡面边框 ────────►│ 2. 属性提示（缩候选集）   │──┤
                    │    边框色相 → 四属性      │  │
                    └─────────────────────────┘  │
                    ┌─────────────────────────┐  │
   卡面文字 ────────►│ 3. OCR 卡名/角色名（加成）│──┘
                    └─────────────────────────┘
```

**属性提示**用的是游戏 UI 的固有特征：四属性边框颜色色相差异明显（强力红 ≈0°、快乐橙 ≈30°、纯洁绿 ≈120°、酷炫蓝 ≈210°）。取外圈高饱和像素做色相软投票，置信度够高时把候选集缩小到对应属性。

这里有个防御设计：**如果属性提示把正确答案排除了**（指纹最高分反而下降），自动退回全库重搜。启发式信号只做加速，不做否决。

**星级不做视觉估计**。数星星对缩放和抗锯齿极其敏感，可靠性差。星级直接从指纹匹配到的卡牌记录里读——既然卡都认出来了，星级、属性、技能自然是准确的。

### 2.5 判定分三档

```
matched    分数 ≥ MATCH_THRESHOLD(0.66) 且与第二名差距 ≥ AMBIGUOUS_GAP(0.03)
                                            → 直接采信
ambiguous  分数低于采信线，或前几名咬得很近   → 列出候选，人工点选
unknown    分数 < UNKNOWN_FLOOR(0.55)        → 可能是指纹库还没有的新卡
```

**三个阈值，不是两个。**``UNKNOWN_FLOOR`` 和 ``MATCH_THRESHOLD`` 回答的是
**不同问题**：前者是"有没有候选"，后者是"敢不敢自动采信"。把它们合成一个
会出事 —— 实测真实截图上有 16 个格子分数落在 0.60~0.66，正确卡其实就是
top-1，只是分数偏低；用一个阈值会把它们全判成 ``unknown``，
用户连候选列表都看不到（第 6 轮踩过这个坑，改动前 71 个 unknown、改动后 0 个）。

**阈值必须跟着特征方案一起标定。** 换特征一定会改分数尺度：全局直方图时代
``MATCH_THRESHOLD = 0.74`` 合理（分数均值 0.808）；改用分块颜色后分数整体
下移到均值 0.758，沿用 0.74 立刻让 71/140 变成 unknown。现在的 0.66 是这么定的：
真实截图上 ``[0.66, 0.76) 且 gap ≥ 0.03`` 的 13 个格子逐格人工核验**全部正确**。

把"不确定"显式暴露出来，比强行给一个错误答案好得多。`ambiguous` 的候选列表 + 卡图缩略图，人工确认一次只要一两秒。

### 2.6 自动网格切分：为什么最后选了自相关

一张截图里有多个卡面，必须先切分。这条路上试了三种方案，前两种都不够稳：

| 方案 | 原理 | 失败场景 |
| --- | --- | --- |
| 背景色差异 | 取四边中位数当背景色，差异大的算内容 | **卡框紧贴、中间没有背景像素**时，所有卡被识别成一个巨大内容块 |
| 局部纹理方差 | 卡面有纹理、卡框平坦 | 卡面本身有大片平坦区域（天空、纯色底）时，该列被判为"无内容"，投影断裂 |
| **自相关找周期** ✅ | 卡牌列表是**等距重复结构**，边缘能量曲线在周期 T 处自相关出峰 | 需要网格规整（游戏列表页基本都满足） |

自相关方案对「卡框紧贴 / 有间隙 / 任意边框色 / 卡面平坦」全部免疫，因为它找的是**重复性**而不是**内容**。实测 7 种布局全部切对。

实现上有三个坑，都是实测踩出来的：

**坑 1：相位搜索范围必须限制。** 等分切分默认从 0 开始，但真实截图左侧常有一条外边距，所以要用相位搜索对齐到边缘能量最高的位置。但如果相位搜索放开到 `[0, period)`，网格会被整体推出画布，最后一格被裁掉 —— 格数就少一个。正确范围是 `[0, total - count*period]`。

**坑 2：不能只取最强的自相关峰。** 卡面图案自身有重复结构，它的峰可能比网格周期还强。实测遇到过卡面高度 90px、网格周期 100px 的情况，最强峰落在 90 上。做法是**返回按强度排序的候选周期列表，依次尝试**，直到有一个能推出合理的格数。

**坑 3：搜索范围上限不能用 `n/2`。** 看似应该限制在 `n/2`（至少容纳两个周期），但一维差分让边缘曲线比原图少 1 个像素：H=200 的两行网格周期正好是 100，而 `n=199` 时 `n//2 = 99` —— 真周期刚好被截断。放宽到 `n` 是安全的，因为周期过大会被格数合理性校验挡掉。

格数合理性校验：`total / period` 必须接近整数（容差 0.18）。这能滤掉"卡片内部图案的重复"这类假周期 —— 宁可返回"没检测到网格"让上层走别的策略，也不要切出错误的格数。

### 2.7 换用「方形缩略图」建库 —— 一次决定性的修正

§2.3 当时假设「游戏缩略图带了边框、星级、属性图标，取景和 Bestdori 原图不完全一致」，
靠多档裁切兜住。**这个假设本身就是错的** —— 真正的问题不是"多了边框"，而是
**画幅根本不同**。

#### 两套资源

Bestdori 上同一张卡有两套图：

| 资源 | 尺寸 | 取景 |
| --- | --- | --- |
| `characters/resourceset/{名}_rip/card_{normal\|after_training}.png` | 1334×1002 横向 | 完整卡面（半身 + 背景） |
| `thumb/chara/card{id//50:05d}_rip/{名}_{normal\|after_training}.png` | **180×180 方形** | **脸部 / 上半身特写** |

第二套是 Bestdori 自己卡片列表页（`/info/cards`）用的缩略图，地址从站点的
`app.js` 里挖出来：

```js
"/assets/"+server+"/thumb/chara/card"+Math.floor(id/50).toString().padStart(5,"0")
   +"_rip/"+resourceSetName+"_"+(trained?"after_training":"normal")+".png"
```

游戏内「成员一览」等界面的卡面格是**方形脸部特写**，取景与后者一致，
与横向原图差了一倍多的画幅。pHash 把整图压成 32×32 看低频结构，
同一张脸在两套画幅里落点完全不同 —— 所以旧方案只能"猜角色"。

#### 实测对照（同一批 140 个真实卡面格）

| 指标 | A. 横向原图库 | B. 方形缩略图库 |
| --- | --- | --- |
| 库规模 | 3874 变体 / 2284 卡 | 3865 变体 / 2280 卡 |
| 置信度 均值 / 中位 | 0.775 / 0.774 | **0.808 / 0.792** |
| 置信度 最大 | 0.811 | **0.918** |
| 与次优差距 中位 / 最大 | 0.006 / 0.039 | **0.013 / 0.132** |
| 产品阈值下 `matched` | 16/140 = 11.4% | **57/140 = 40.7%** |

两库的 top-1 答案在 140 格中几乎全部不同，逐一并排渲染人眼核对后确认
**B 才对**（例：游戏格里那顶贝雷帽只有 B 的「不想忘记的时刻」有；A 给的是
绿眼棕发，游戏格是蓝灰眼浅棕发）。

#### 被证否的两条路

- **方形中心裁切原图**：把 1334×1002 按短边居中裁成方形再比对，
  top1 从 0.742 掉到 0.695、gap 从 0.031 掉到 0.008 —— **更差**。
  说明游戏格的取景不是原图的简单方形裁切。
- **固定裁切对**：怀疑「4×4 全组合取最小」抬高分数底线，改成固定第 i 档 × 第 j 档。
  实测最好的一种也只有 27.9%，**低于全组合的 37.9%** —— 全组合在吸收每格的
  取景抖动，是有用的，不该去掉。

#### 取景本来就一致（一个差点走错的地方）

中途从一个探针（`crop_scale_probe.py`）里读出过「游戏格 ≈ 缩略图中心 53%」，
据此以为游戏格的取景比缩略图紧一倍，还去扫了「库端该裁到多少」。**这是误读** ——
那个探针比较的是「查询端第 i 档裁切 × 库端第 j 档裁切」，最优组合
（查询 0.525, 库 0.60）的比值 0.60/0.525 ≈ 1.14，说明**两者基本同框**，
而不是"游戏格只截了缩略图的 53%"。

后来用一个直接的测法定死了这件事（`.bdh-test/measure_zoom.py`）：拿换库后
**高置信度命中**的真实格子（matched 且 gap ≥ 0.05，几乎不可能错），对正确那张
缩略图扫遍中心裁切比例 z，取相似度最大的那个。34 个参照格的结论：

```
最优取景系数 z*：中位 1.000  均值 0.977  最小 0.800  标准差 0.039
```

**z\* = 1.00，游戏格和缩略图取景本来就一致** —— 这正是换库效果显著的根本原因。
库端就用缩略图原样，不做任何裁切。

（教训：跨档位组合的探针，输出的是"比例关系"，不能直接读成"绝对取景"。
要绝对量就单独测一次。）

#### 顺手修掉的一个真 bug

`estimate_attribute_icon`（属性提示）原来筛像素的条件是
``(sat >= 60) & (val <= 245)``。那个 ``val <= 245`` 本意是"排掉白色面板"，
但**四属性标准色里三个的 V 就是 255**（``#FF4D4D`` / ``#4D9BFF`` / ``#FFB84D``），
图标本体被当成白色滤掉，剩下的全是卡面画色 —— 于是提示会**自信地报出错误属性**，
把正确答案从候选集里筛走。

白色本身 ``sat ≈ 0``，靠饱和度已经排除了，这个条件纯属有害。改成
``(sat >= 60) & (val >= 30)``（只额外排掉近黑噪声像素）：

| 场景 | 修前 | 修后 |
| --- | --- | --- |
| 合成格（V=255 纯色图标） | 8 格错 3，置信度 0.34~0.51 | **8/8 命中，置信度 0.75~1.00** |
| 真实截图（34 个高置信参照格） | 34/34 | **34/34**（无回归） |
| edge_cases 属性提示 A/B | 开 48% / 关 100% | 开 88% / 关 100% |

这个 bug 在真实截图上一直没暴露：游戏里的属性图标不是纯色 255，所以老条件
侥幸没伤到它。是补合成基准时才撞出来的。回归测试见 `tests/test_ui_hints.py`。

#### 换库后暴露的：匹配阈值该调了

分数分布换库前后完全不同：

| | 换库前（横向原图） | 换库后（方形缩略图） |
| --- | --- | --- |
| 正确匹配的分数 | 0.74 ~ 0.81 | **0.94 ~ 0.99**（合成）/ 0.85 ~ 0.92（真实） |
| 错误匹配的分数 | 0.75 ~ 0.79 | **0.74 ~ 0.78** |

换库前所有分数都挤在 0.76 附近，`MATCH_THRESHOLD = 0.74` 是合理的；
换库后正确与错误的分数**分得很开**，0.74 这个阈值明显偏低 —— 合成基准里
出现了把 0.775 的错误答案标成 `matched`、而正确答案只有 0.742 的情况。

**这是下一步最值得调的一个参数**，但需要真实 ground truth 来标定（140 个真实格
里只有 34 个能当参照），本轮没动它，只是把现象记在这里。

#### 两个实现坑

1. **分桶目录名是卡牌 ID 派生的**：`id // 50` 补零 5 位（id=158 →
   `card00003_rip`，id=2468 → `card00049_rip`）。按资源名猜目录会整片 404。
2. **111 个 `resourceSetName` 被两张卡共用**（涉及 231 张卡）。建
   `resourceSetName → cardId` 的反查表只能留住一张卡，实测**静默丢掉 125 张卡**。
   必须**逐卡**解析文件路径。生产代码 `index.py` 一直是逐卡遍历的，没这个问题；
   反而是实验脚本踩了这个坑，导致中途得出过"缩略图覆盖率低 5%"的错误结论。

#### 落地形态

`Settings.image_source`（`thumb` 默认 / `original`）决定用哪一套卡图：

- 缓存目录分离：`cache/thumbs/{server}/` vs `cache/images/{server}/`
- 指纹库分离：`fingerprints.{server}.thumb.npz` vs `fingerprints.{server}.npz`
  （不分的话两边会轮流覆盖，识别结果莫名漂移）
- `.missing` 负缓存标记同步跟着来源走
- CLI `--source thumb|original`，GUI 沿用设置并在启动日志里显示来源

顺带一个数字：缩略图全套 3625 张只有 **80 MB**，而横向原图是 **1~2 GB** —— 建库
从"十几分钟 + 2 GB"降到"几分钟 + 80 MB"。

#### 还没解决的

换库修掉的是**取景不一致**，不是**区分度**。同角色同属性的多张卡之间，
64 bit 的 pHash + dHash 熵不够分给 3800+ 张库，top-1 与 top-2 差距的中位仍
只有 0.013。要再上一个台阶得换更强特征（SIFT 局部特征 / embedding）或加
互补信号（OCR 卡名、OCR 战力数字）。**当前的人工校正流程是设计的一部分。**

### 3.1 GUI 的分层原则

桌面界面是**纯外壳**，一条业务逻辑都不重复实现：

| 界面动作 | 实际调用的函数 |
| --- | --- |
| 同步卡池资料 | `BestdoriClient.fetch_catalog()` |
| 构建指纹库 | `vision.index.build_index()` |
| 开始识别 | `vision.recognize.recognize_image()` |
| 写入清单 | `Inventory.absorb_recognition()` |
| 生成导入计划 | `bridge.build_import_plan()` |
| 实际写入 | `bridge.PlaywrightImporter.run()` |
| 导出 | `inventory.export.to_csv/json/markdown` |

好处是命令行、Web、桌面三条路径的行为天然一致，测试也只需要覆盖一层。
`gui/workers.py` 里的 `Worker(QThread)` 负责把上述同步函数挪到后台线程，
`say(str)` 回调转成 Qt 信号刷到界面上；任务函数内部**不碰任何 Qt 对象**。

卡图缩略图走 `ThumbnailLoader`：线程池里取图（多半命中本地缓存），
回主线程再构造 `QPixmap`（Qt 要求 GUI 对象只能在主线程建）。
图没到之前先放占位块，到了再补 —— 避免一次性加载上千张卡图把窗口拖死。

### 数据流

```

bdh scan / GUI①   截图 ──► 切分 ──► 特征 ──► 检索 ──► ~/.bestdori-helper/inventory.json
GUI②              人工修正 ──► 改写清单（移除错识别的，加入正确的）

```

### 4.1 公开数据接口（无需登录）

| `GET /api/characters/all.2.json` | 全部角色，实测 268 名 |
| `GET /api/bands/all.1.json` | 全部乐队，实测 111 支 |

多语言数组的下标顺序（实测确认）：

```
[0] 日本語   [1] English   [2] 繁體中文   [3] 简体中文   [4] 한국어
```

### 4.2 卡图资源与四个坑

两套资源，用途不同（选择依据见 §2.7）：

```
# ① 方形缩略图 180×180 —— 建指纹库用这套（默认）
https://bestdori.com/assets/{server}/thumb/chara/card{id//50:05d}_rip/{resourceSetName}_{normal|after_training}.png

# ② 横向原图 1334×1002 —— 展示用
https://bestdori.com/assets/{server}/characters/resourceset/{resourceSetName}_rip/card_{normal|after_training}.png
```

**坑 1：必须带 User-Agent。** 否则 nginx 返回 403，或返回 SPA 首页 HTML（HTTP 200 + `text/html`），很容易被误判为"图片存在"。

**坑 2：约 6.5% 的卡没有 `card_normal.png`。** 实测抽查 200 张有 13 张缺失，集中在：

| 卡牌类型 | 占比 |
| --- | --- |
| `birthday` 生日卡 | 7/13 |
| `campaign` 活动赠送卡 | 4/13 |
| `limited` / `kirafes` | 2/13 |

这些卡的卡面**只存在于 `card_after_training.png`**。代码里由 `resolve_variants()` 处理回退，并对确认不存在的资源写 `.missing` 标记做负缓存，避免每次重建都重复请求。

**坑 3：`/api/cards/{id}.json` 这种单卡路径不存在**，会返回 SPA 首页（HTTP 200 + HTML）。必须拉全量接口后本地索引。

**坑 4：缩略图的目录名是卡牌 ID 派生的。** 数字是 **50 张一桶**的桶号（`id // 50` 补零 5 位），不是资源名里的哪个片段。另外 **111 个 `resourceSetName` 被两张卡共用**（涉及 231 张卡）—— 用 `resourceSetName → cardId` 反查表会静默丢卡。

### 4.3 写入端

通过分析 Bestdori 的前端 bundle（`app.js` 路由表 + `ProfileCards` chunk），确认卡牌登记页是：

```
/profile/manager    Profile Manager  创建档案（服务器 / 活动 / 大师等级 / 技能等级）
/profile/cards      Profile Cards    ← 登记持有卡牌，写入目标
/profile/items      Profile Items    区域道具
/profile/preferences
```

`ProfileCards` 模块内部使用的设置键：`profile/cards/displayMode`、`profile/cards/optionSortBy`，添加卡片的入口是 `profile/cards/add`。这些都是**登录态账号数据**。

Bestdori 是 Vue SPA，路由由前端接管，直接 GET 这些路径只会拿到 14084 字节的 SPA 外壳。

### 4.4 三层导入方案

因为无法在未登录状态下验证写入接口的请求体，设计上提供三层方案，从稳到快：

| 层级 | 方案 | 依赖 | 说明 |
| --- | --- | --- | --- |
| 1 | **导入计划文件** | 无 | 算出「本地有、远端没有」的卡，导出 JSON/CSV/ID 列表。最稳，零风险 |
| 2 | **浏览器自动化** | Playwright | 复用已登录的浏览器会话，在 `/profile/cards` 页面按卡名搜索逐张添加。默认 dry-run |
| 3 | 直接调内部接口 | 需自行抓包 | 最快但最脆，Bestdori 改版即失效，本工具不预置 |

第 2 层的抗改版设计：**不硬编码单一选择器**，每个操作给一组候选，取第一个命中的。全部落空时用 `--inspect` 打印页面上的输入框/按钮/类名，把新选择器补进 `SelectorConfig` 即可。

## 5. 验证结果

三层验证：单元测试（离线）→ 端到端合成截图（真实卡图）→ 边界场景专测。

### 5.1 识别准确率（`scripts/e2e_check.py`）

> ⚠️ **这个基准在第 5 轮被大改过，历史数字不可直接比较。**
>
> 旧版本合成的是**长方形**格子（230×173 等），而卡图当时是 1334×1002 横向 ——
> 两者长宽比都是 1.33，等于"拿原图缩放进格子"，所以能刷到 97.6%。
> 真实游戏格实测是 **170×170 正方形**，这个基准从一开始就没模拟对。
> 换成方形缩略图建库后，长方形格子会把方图横向拉伸 33%，基准直接垮到 31.7%。
>
> 现在基准改成：**正方形格 + 画布尺寸正好等于 ``cols*cell × rows*cell``**
> （``grid`` 模式是等分切分，画布多留外边距会让切出的框和粘贴位置错位）、
> **按卡的真实属性给卡框上色并画右上角属性图标**（游戏里卡框和图标就是属性
> 指示器，早期版本按槽位轮流取色，等于给属性提示喂假信号）。

修正后（80 张卡建库，56 个有效格）：

| 场景 | 布局 | 格子 | 附加难度 | 有效格 Top-1 |
| --- | --- | --- | --- | --- |
| A 标准 | 4×2 | 170 | — | **100%** |
| B 小图 | 3×3 | 140 | — | **100%** |
| C 压缩 | 5×2 | 160 | JPEG 质量 55 | **100%** |
| D 色偏 | 4×2 | 170 | 亮度 0.82 / 饱和度 0.7 | **85.7%** |
| E 极小 | 6×2 | 110 | JPEG 质量 70 | **100%** |
| F 取景偏松 | 4×2 | 170 | 中心裁 80% | **100%** |
| G 取景偏紧 | 4×2 | 170 | 中心裁 42% | **50.0%** |
| **合计** | | | | **91.1%**，误判 0 |

- **误判率 0** —— 没有一个错误答案被标为 `matched`
- **可用率 100%** —— 正确 + 歧义（可由人工点选）覆盖全部有效格
- 与第 9 轮**加卡框贴合之前完全持平**（91.1%），而误判从 1 降到 0 —— 那 1 例
  原本被自动采信成了错误答案，现在落到 `ambiguous`
- 歧义集中在同角色的视觉相似卡上（例如「白金 燐子 · GOGO WEGO！」vs「白金 燐子 ·
  重叠的蓝色蔷薇」）以及取景严重失真的 G 组

> **这个基准的几何与真实游戏有一处差异，值得留意**：`make_screenshot` 把卡框
> 画满整个格子（`draw.rectangle` 一直铺到格子边界），相邻卡框直接相接、**没有
> 间隙**；而真实游戏截图里卡框只占格子的 85% 左右、卡框之间还有 20~25px 的间隙。
> 所以在卡框贴合这一项上，基准能验证的是"不该动的地方别乱动"，验证不了
> "该贴的地方贴住了"—— 后者只能靠真实截图（§5.4）。给基准加一组"带间隙"的布局
> 是后续该做的事。

测试用的卡池刻意从同一角色取多张卡（每个角色取 7 张），专门制造难例。

### 5.2 自动网格切分（`scripts/edge_cases.py`）

| --- | --- | --- |

### 5.3 属性提示 A/B 对照

| 配置 | 合计 Top-1 | 误判 |
| --- | --- | --- |
| 属性提示 **开** | 88.0%（22/25） | 0 |
| 属性提示 **关** | 100%（25/25） | 0 |

**修掉 `val <= 245` 那个 bug 之前这里是 48% vs 100%**（见 §2.7），修完差距收窄到 12%。

剩下这 12% 是**属性提示的固有代价**：它是**硬过滤** —— 提示把候选集缩到某个属性后，
如果提示错了，正确答案就被整片排除，而防御逻辑只在 ``hint.confidence < 0.45``
时才退回全库（提示"自信地错"时不退）。合成图标与游戏里的真图标并不完全一致，
这 3 个失败格大概率是合成失真造成的，**真实数据上提示是 34/34 全中**。

> 后续可以考虑把「硬过滤」改成「同属性候选 +0.02 的软加成」—— 提示就永远不可能
> 排除正确答案，只影响排序。需要先在真实截图上验证收益。

### 5.4 真实截图（最重要的一项）

合成基准再像也只是像。真正的检验是用户那 5 张《BanG Dream!》国服「成员一览」截图
（2400×1080，4×7 = 28 格/张，共 140 格）。

```
bdh scan Photo --mode grid --rows 4 --cols 7 \
    --region 0.29333,0.27037,0.79,0.9 --no-ocr
```

| 指标 | 第 5 轮前（横向原图） | 第 5 轮（方形缩略图） | 第 6 轮（+4×4 分块颜色） | **第 7 轮（+SIFT 几何校验）** | **第 9 轮（+卡框贴合）** |
| --- | --- | --- | --- | --- | --- |
| `matched`（可直接采信） | 16/140 = 11.4% | 56/140 = 40.0% | 63/140 = 45.0% | 139/140 = 99.3% | **140/140 = 100%** |
| `ambiguous`（列候选待点选） | 123 | 77 | 77 | 1 | **0** |
| `unknown`（无候选） | 1 | 7 | 0 | 0 | 0 |
| top-1 认出的画正确 | — | — | — | 137/137 = 100% | 137/137 = **100%** |
| 置信度 均值 / 最大 | 0.775 / 0.811 | 0.808 / 0.918 | 0.758 / 0.880 | — | — |
| 与次优差距 中位 / 最大 | 0.006 / 0.039 | 0.013 / 0.132 | 0.028 / 0.213 | — | — |
| 属性提示准确率 | 28/28 = 100% | 34/34 = 100% | — | — | — |

> 注意第 6 轮的**置信度均值反而下降** —— 这是分块颜色让"不匹配的候选分数掉得更多"
> 的结果，也就是我们要的分离度。分数尺度变了，所以阈值必须一起重标定（§2.5）。
>
> 第 6 轮还消掉了全部 7 个 `unknown`：那批格子分数落在 0.60~0.66、正确卡其实
> 是 top-1，只是被"单阈值"误判成"库里没有"。拆出 ``UNKNOWN_FLOOR`` 后它们
> 回到 ``ambiguous``，用户能点选。

前 5 格的分数从 0.74~0.80 直接跳到 **0.852 ~ 0.918**。并排渲染人眼核对
（``.bdh-test/verify_thumbs.py``）确认 top-1 正确，例如游戏格里那顶贝雷帽
只有「不想忘记的时刻」对得上。

**第 6 轮那 45% 是"只看全局特征"时能自动采信的比例，不是识别能力的天花板。**
第 7 轮加上 SIFT 几何校验后，137 个可评估格的 top-1 全部正确 —— 全局特征分不出
"同角色同属性的不同卡"，而 SIFT 的几何一致性是"是不是同一张画"的硬证据（§2.2b）。
换库修掉的是"取景不一致"，不是"区分度"；真正解决区分度的是几何校验。

第 9 轮加了卡框贴合后，自动采信补满到 **140/140**（最后一格原来是 `ambiguous`，
框贴合后 SIFT 内点更明确）。卡号准确率 99.3%（136/137）—— 差的 1 格是 Bestdori 上
两张卡共用同一张卡图，从图像上无法区分，见 §2.2d。

## 6. 已知限制与后续方向

### 当前限制

| 限制 | 影响 | 缓解 |
| --- | --- | --- |
| ~~指纹区分度~~ | 已解决 | **SIFT 几何校验**：top-1 67.9% → 100%（见 §2.2b） |
| 几何校验需要 opencv | 没装时自动降级，但准确率掉到 67.9% | 已列入 requirements 并在日志里明确告警 |
| **属性提示做硬过滤会伤准确率** | 实测：开提示 59.1% vs 不开 67.9% —— 提示"自信地判错"时会把正确的卡整个排除在候选之外 | 几何校验路径**刻意不用属性提示限制候选**，直接全库粗筛；提示只在退回路径里当参考 |
| 单格耗时约 2.3s | 100 格截图约 4 分钟 | 库端特征有会话内缓存；候选数首轮 30、只在没确认时才扩到 200 |
| 阈值与特征耦合 | 换特征必须同步重标定 `MATCH_THRESHOLD` | 已在常量注释里写明历史与依据；`UNKNOWN_FLOOR` 与 `MATCH_THRESHOLD` 职责分离 |
| 属性提示是硬过滤 | 提示"自信地错"时正确答案被整片排除，只在 `conf < 0.45` 时退回全库 | 可改成同属性候选软加成（见 §5.3） |
| 指纹库要下载卡图 | 默认缩略图 80 MB / 几分钟；`--source original` 则 1~2 GB / 十几分钟 | 增量更新；`--no-trained`；`--cards` 试跑 |
| 换 `--source` 要重建库 | 两套画幅不同，特征不可比 | 两库分文件存，互不覆盖；不做隐式迁移 |
| 新卡滞后 | Bestdori 收录后才能认 | 报 `unknown` 而非误判 |
| 整屏 UI 截图必须给 `--region` | 不给会切到 UI 上（实测 28 格切成 156 格） | CLI / GUI 都支持 `--region` |
| 自动化导入依赖页面结构 | Bestdori 改版需重新校准 | 候选选择器组 + `--inspect` |
| 空槽位会给出低分候选 | 空位被报为 `unknown` | 分数低于阈值一律 `unknown`，不会误报 |
| **卡框贴合只向内收缩** | 格子边界已经切进本格卡面内部时补不回来（实测第 3~5 张截图的格子上边被切掉约 7px） | 刻意如此：向外扩展有吃到相邻卡面的风险，那正是要消除的问题。SIFT 对整体裁切免疫，少 7px 不影响识别 |
| **共用卡图的卡无法区分** | 111 个 `resourceSetName` 被多张卡共用，卡号可能不是用户实际持有的那张 | 排序键加了卡号升序保证结果可复现；需人工确认（见后续方向 3） |

### 后续方向

1. **属性提示改软加成** —— 把「硬过滤」换成「同属性候选 +0.02」，提示就不可能
   排除正确答案，只影响排序。
2. **给合成基准加"带间隙"的布局** —— 现在的 `make_screenshot` 把卡框画满整个格子
   （相邻卡框相接、无间隙），与真实游戏（卡框占格子约 85%、卡框之间 20~25px 间隙）
   不符。结果是卡框贴合在这个基准上只能验证"不该动的地方别乱动"，验证不了
   "该贴的地方贴住了"。加一组带间隙的布局，贴合效果才能在基准上被量化。
3. **给"共用卡图"的多张卡做并列展示** —— Bestdori 上有 111 个 `resourceSetName`
   被多张卡共用（§2.2d）。现在 tie-break 按卡号升序选一张，但正确的做法是把同图
   的几张卡一起列出来让用户确认。需要在 `Catalog` 层加"同图卡"索引。
4. **OCR 实测调优** —— 加 OCR 卡名/战力数字做交叉校验（战力数字能把候选从 2468 降到几十）。
5. **特训/未特训双形态** —— `trained` 字段可用来预填 Bestdori 的特训状态。
6. **大师等级 / 技能等级识别** —— Profile Manager 需要 `masterRank` / `skillLevel`。
7. **卡组推荐对接** —— 对接 Bestdori Team Builder 的最优编队计算。
